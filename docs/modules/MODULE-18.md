## 1. Purpose

Module 18 is the full alert delivery and routing system. It takes alerts
generated by Module 17 (Continuous Monitoring) and handles:

- **Routing** — direct alerts to the right delivery channels based on type/priority
- **Notification** — format and deliver alerts via channels (email, SMS, webhook, in-app)
- **Escalation** — if an alert isn't acknowledged within a timeframe, escalate it
- **Templates** — standardized notification templates per alert type
- **Digest** — batch low-priority alerts into periodic digests

```
Module 17 → alert.created event
                ↓
        Module 18 Alert Router
                ↓
        ┌───────┴───────┐
        │               │
   Immediate send    Digest queue
        │               │
   Notification    Periodic digest
   channels        (email summary)
```

## 2. Architecture — Two Layers

### Layer A (In-Memory MVP — Sandbox)
- `AlertRouter` — route alerts to channels by priority/type
- `NotificationService` — mock delivery (logs, in-memory queue)
- `EscalationPolicy` — time-based escalation rules
- `AlertTemplate` — notification message templates
- `AlertDigest` — collect low-priority alerts, generate digest
- `AlertManager` — orchestrator combining all components

### Layer B (Production — REQUIRES EXTERNAL INFRASTRUCTURE)
- Real email/SMS delivery (SendGrid/Twilio)
- WebSocket push notifications
- Slack/Teams integration
- Persistent escalation state (Redis)
- Real-time alert stream (Kafka)

## 3. Key Components

### 3.1 AlertRouter
- `route(alert)` — determine delivery channels based on priority/type
  - URGENT → immediate: email + SMS + webhook + in-app
  - HIGH → immediate: email + in-app
  - MEDIUM → immediate: in-app, digest: email
  - LOW → digest only
- `add_routing_rule(rule)` — custom routing rules
- Routing rules: match by alert_type, priority, target_type

### 3.2 NotificationService
- `send(channel, notification)` — mock send to a channel
- `get_delivery_log()` — retrieve delivery log
- Channels: EMAIL, SMS, WEBHOOK, IN_APP, SLACK
- Each delivery is logged with timestamp, status (SENT, FAILED, PENDING)

### 3.3 EscalationPolicy
- `EscalationLevel` — defines escalation tiers
  - Level 0: original recipients
  - Level 1: team lead (after 15 min)
  - Level 2: department head (after 1 hour)
  - Level 3: security operations center (after 4 hours)
- `check_escalation(alert)` — check if alert needs escalation
- `escalate(alert)` — escalate to next level
- `EscalationChain` — ordered list of escalation contacts

### 3.4 AlertTemplate
- `render(alert, template_name)` — render notification text from template
- Predefined templates per AlertType
- Template variables: alert_id, target_type, target_id, priority, changes, timestamp

### 3.5 AlertDigest
- `add(alert)` — add alert to digest queue
- `generate_digest()` — generate digest summary of queued alerts
- `clear()` — clear digest queue after sending
- Digest groups by target_type and summarizes

### 3.6 AlertManager
- `process_alert(alert)` — full pipeline: route → template → send → digest
- `check_escalations()` — check all pending alerts for escalation
- `get_statistics()` — alert counts by type, priority, status
- Orchestrates router, notification, escalation, digest

## 5. Acceptance Criteria

1. AlertRouter routes URGENT alerts to immediate multi-channel delivery
2. AlertRouter routes LOW alerts to digest queue
3. NotificationService delivers and logs notifications
4. Notification templates render correctly for all alert types
5. Escalation policy escalates unacknowledged alerts by timeframe
6. Alert digest batches and summarizes low-priority alerts
7. AlertManager orchestrates the full alert pipeline
8. Alert statistics provide counts by type, priority, status
9. Custom routing rules can be added
10. Events are published for escalations
